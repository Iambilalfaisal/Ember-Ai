# 0003. Database conventions

- Status: accepted
- Date: 2026-11-05

## Context

Every later module stores tenant data in PostgreSQL. The conventions below are expensive
to change once tables exist, so they are fixed in the foundation (AGENTS.md section 4).

## Decision

- **Ids:** `id` is a native `UUID` primary key generated by the application (`uuid.uuid4`),
  so ids are known before flush and rows can be created offline or in batches.
- **Tenancy:** every business table has `tenant_id UUID NOT NULL` with an index, via
  `TenantMixin`. There is no foreign key to the tenants table yet; `identity` owns that
  table (F4) and will decide on the constraint.
- **Timestamps:** `created_at` and `updated_at` are `timestamptz`, NOT NULL. Values are set
  in Python in UTC (`default` and `onupdate`) so they are available after flush without a
  refresh round trip in async code. A server default of `now()` covers raw SQL inserts.
  Every connection runs with `timezone=UTC`.
- **Constraint names:** one metadata naming convention (`pk_`, `uq_`, `ck_`, `fk_`, `ix_`
  prefixes) so Alembic autogenerate produces stable, droppable names.
- **Transactions:** one per request. `get_session` commits on success and rolls back on
  any exception, and is declared with `scope="function"` so the commit happens before the
  response is sent. A failed commit reaches the client as an error, never as a false success.
- **Migrations:** Alembic with an async engine. The URL comes from `Settings`, not from
  `alembic.ini`. `env.py` imports `ember.modules.<name>.models` for every module so
  autogenerate sees all tables. The first migration enables the `vector` extension.
- **Deferred on purpose:** row-level security, partitioning, read replicas and an outbox
  are cheap to add later and are not part of the foundation.

## Consequences

- Services never commit, so a service call is safe to compose inside one request.
- Python-side timestamps depend on application clocks being roughly in sync. That is
  acceptable at current scale; a database-clock-only scheme would need a refresh after each
  update.
- Tenant isolation currently relies on `TenantScopedRepository` (F3), not on the database.
  Row-level security can be added later as a second layer without changing the schema.

## Alternatives considered

- **Server-generated UUIDs (`gen_random_uuid()`):** ids would not be known until the insert
  returns, which complicates building related objects in one unit of work.
- **Database-only timestamps:** simpler SQL, but async SQLAlchemy would need
  `eager_defaults` or a refresh to read them back after an update.
- **Default dependency scope for `get_session`:** the commit would run after the response is
  sent, hiding commit failures from the client.
